1: # BSD Downloader
2: 
3: 一个用 C++20 写的多线程 HTTP/HTTPS 下载器，支持断点续传、分片下载、哈希校验、全局限速、代理。
4: 
5: 项目拆成两部分：
6: 
7: - **`bsd_core`** —— 下载核心，编译为 `bsd_core.dll`（Windows）/ `libbsd_core.so`（Linux、macOS），只暴露 [`include/bsd/bsd_core.h`](include/bsd/bsd_core.h) 里的 `extern "C"` C API，方便被 GUI 或其它调用方嵌入。
8: - **`bsd`** —— 命令行客户端，用 CLI11 解析参数，只通过 C API 调用核心，不直接依赖 libcurl / fmt / CLI11 的 C++ 接口。
9: 
10: ## 特性
11: 
12: - **多线程分片下载** —— 按线程数与文件大小自适应切片，多个 worker 并发下载
13: - **核心 / CLI 分离** —— 核心是动态库 + 纯 C 接口，CLI 只是它的一个调用方，可以另写 GUI
14: - **断点续传** —— 中断后 `-c` 从上次进度继续，靠 `.meta` + ETag/Last-Modified 校验服务器文件是否变化
15: - **哈希校验** —— 支持 `md5` / `sha1` / `sha256` / `sha512`，校验失败自动删除
16: - **重试机制** —— 网络类错误由调用方重试，指数退避
17: - **全局限速** —— `--limit-rate` 限制所有线程的合计速率，而不是每条连接
18: - **自适应分片** —— 分片数与分片大小由线程数和文件大小决定，尽量让所有 worker 都有活干、减少尾部空等
19: - **代理** —— 支持 HTTP/HTTPS 代理
20: - **进度回调** —— 核心每 500ms 回调一次进度，CLI 用它画进度条，GUI 可以直接拿数据
21: - **静默模式** —— `-s` 关闭所有输出
22: - **日志文件 / 日志回调** —— 可选写入日志文件，GUI 可注册日志回调
23: - **自定义请求头** —— `-H` 可重复添加
24: - **自动文件名** —— 优先 `Content-Disposition`，退回 URL 尾段
25: 
26: ## 依赖
27: 
28: - **CMake** >= 3.31
29: - **C++20** 编译器（MSVC 19.29+ / GCC 10+ / Clang 12+）
30: - **vcpkg** 管理第三方库

33:

36: - `fmt` —— 日志格式化
37: - [`CLI11`](https://github.com/CLIUtils/CLI11) —— 仅 CLI 使用，核心库不依赖它
38: - `zlib` —— 间接依赖

105: 
106: ```bash
107: # 下载到当前目录，自动推断文件名
108: bsd https://example.com/video.mp4
109: 
110: # 指定输出文件名
111: bsd https://example.com/video.mp4 -o video.mp4
112: 
113: # 下载到指定目录
114: bsd https://example.com/video.mp4 -d ./downloads
115: 
116: # 16 线程下载
117: bsd https://example.com/video.mp4 -t 16

128: 
129: # 带自定义请求头
130: bsd https://example.com/file -H "Cookie: a=1" -H "Referer: https://example.com"

134: 
135: # 静默模式 + 日志文件

137: 
138: # 多文件下载
139: bsd https://example.com/a.zip https://example.com/b.zip -o a.zip b.zip
140: 
141: # 多文件 + 各自校验

167: ## 工作原理
168: 
169: ### 分片下载
170: 
171: 1. 发 `HEAD` 请求拿响应头，解析 `Content-Length`、`ETag`、`Last-Modified`、`Accept-Ranges`
172: 2. 自适应计算分片：
173:    - 目标片数 = `threads × 8`；
174:    - 片大小 = `文件大小 / 目标片数`，再夹到 `[256KB, 16MB]`；
175:    - 片数上限 4096，最后把文件均分。
176:    这样大文件有足够多的任务喂满线程池，小文件也不会切得过碎。
177: 3. 每个分片独立发 `Range: bytes=start-end` 请求
178: 4. 每个 worker 用 `seekp(offset)` 写入同一个 `.part` 文件
179: 5. 全部完成 → `rename` `.part` 为最终文件，删 `.meta`
180: 
181: **关键点**：
182: 
183: - 每个 worker 独立打开一个 `ofstream`（`in|out` 模式），避免共享流导致的竞态
184: - **不用 `app` 模式**，否则 `seekp` 失效
185: - 所有 worker 结束后才 `rename`，避免文件占用
186: 
187: ### 全局限速
188: 
189: 所有 worker 共享一个 `RateLimiter`：每收到一段数据，先为这段数据在共享时间轴上预约 `bytes / limit_rate` 秒并等待。因为大家都排在同一条时间轴上，总速率就是 `--limit-rate`，而不是“每线程 × limit_rate”。等待过程是分小段 sleep 的，并且可以被取消打断。
190: 
191: ### 断点续传
192: 
193: 下载中会生成两个文件：
194: 
195: - `{name}.part` —— 数据文件
196: - `{name}.meta` —— JSON 元数据，记录 URL、ETag、总大小、每个 chunk 的 `done`
197: 
198: 续传时：
199: 
200: 1. 读 `.meta`，发 `HEAD` 校验：
201:    - URL 一致
202:    - 总大小一致
203:    - ETag 或 Last-Modified 至少一个能对上
204: 2. 校验通过 → 从每个 chunk 的 `begin + done` 继续
205: 3. 校验失败 → 丢弃 `.part` 和 `.meta`，从头下载
206: 
207: **中途崩溃保护**：每下 4MB 自动 flush 数据并保存一次 `.meta`，崩溃后重启能恢复大部分进度。
208: 
209: ### 哈希校验
210: 
211: 下载完成后计算文件的哈希：
212: 
213: - 与 `--checksum` 提供的值比对
214: - 不一致 → **删除文件** + 返回不可重试错误
215: - 一致 → 通过
216: 
217: **注意**：哈希校验失败**不重试**，因为服务器上的文件就是坏的，重试还是同一个。

219: ## 作为库使用（C API）
220: 
221: 最简示例（完整定义见 [`include/bsd/bsd_core.h`](include/bsd/bsd_core.h)）：
222: 
223: ```c
224: #include <bsd/bsd_core.h>
225: #include <stdio.h>
226: #include <stdint.h>
227: 
228: static void on_progress(void* user, uint64_t done, uint64_t total,
229:                         double speed, int finished) {
230:   printf("\r%llu/%llu  %5.1f%%  %.1f MB/s",
231:          (unsigned long long)done, (unsigned long long)total,
232:          total ? 100.0 * (double)done / (double)total : 0.0,
233:          speed / 1048576.0);
234:   if (finished) printf("\n");
235: }
236: 
237: int main(void) {
238:   if (bsd_init() != 0) return 1;
239: 
240:   bsd_options opt = {0};
241:   opt.struct_size = sizeof(opt);
242:   opt.dir = "downloads";
243:   opt.threads = 8;
244:   opt.timeout_seconds = 90;
245:   opt.limit_rate_bytes_per_second = 4ULL * 1024 * 1024;  /* 4 MiB/s，全局 */
246: 
247:   bsd_handle* handle = bsd_handle_create(&opt);
248:   if (!handle) {
249:     fprintf(stderr, "handle: %s\n", bsd_last_error());
250:     bsd_cleanup();
251:     return 1;
252:   }
253: 
254:   bsd_request req = {0};
255:   req.struct_size = sizeof(req);
256:   req.url = "https://example.com/big.iso";
257: 
258:   int rc = bsd_download(handle, &req, on_progress, NULL);
259:   if (rc != BSD_OK) fprintf(stderr, "download failed: %s\n", bsd_last_error());
260: 
261:   bsd_handle_destroy(handle);
262:   bsd_cleanup();
263:   return rc == BSD_OK ? 0 : 1;
264: }
265: ```
266: 
267: 要点：
268: 
269: - `bsd_download` 是阻塞调用；GUI 请在单独的工作线程里调用它。
270: - `bsd_handle_cancel` 线程安全，可从 UI 线程调用；下载会尽快停下并返回 `BSD_ERROR_CANCELLED`。
271: - 返回码：`BSD_OK` / `BSD_ERROR`（不可重试）/ `BSD_ERROR_RETRYABLE`（可重试）/ `BSD_ERROR_CANCELLED` / `BSD_ERROR_INVALID_ARG`；本线程的错误文本用 `bsd_last_error()` 取。
272: - 一个 `bsd_handle` 持有一个线程池；在同一个 handle 上串行调用 `bsd_download` 可以复用线程池。
273: - 日志默认输出到控制台，可用 `bsd_set_log_file` / `bsd_set_log_callback` 接管；`bsd_set_log_silent(1)` 全部关闭。

319: ## 架构
320: 
321: ```
322: bsd (CLI, CLI11)                     GUI / 其它调用方
323:       │                                     │
324:       └──────────────┬──────────────────────┘
325:                      ▼
326:             bsd_core.dll（extern "C" C API）
327:                      │
328:                 Downloader
329:                  ├─ recover()  续传校验（可选）
330:                  ├─ prepare()  HEAD + buildMeta + planChunksAdaptive
331:                  ├─ dispatch() 提交分片任务到 ThreadPool，等完成
332:                  │   └─ download_chunk()  worker 函数
333:                  │        ├─ RateLimiter::acquire()  全局限速
334:                  │        └─ 每 4MB flush + 保存 .meta
335:                  └─ finalize() rename + 哈希校验
336: ```
337: 
338: **线程模型**：
339: 
340: - 每个 `bsd_handle` 一个 `ThreadPool`（`-t` 控制大小）
341: - 一个进度线程（核心内部，每 500ms 调用一次进度回调）
342: - 每个分片一个 worker 任务
343: - `downloaded_bytes` 用 `std::atomic<uint64_t>`
344: - `meta_` 用 `std::mutex` 保护
345: 
346: ## 已知限制
347: 
348: - **不支持 HTTP/2**：libcurl 默认 HTTP/1.1
349: - **不支持多个 URL 并发下载**：CLI 内串行，避免抢带宽
350: - **限速是客户端节流**：按字节数在写盘前等待，瞬时速度会有小幅波动，长期平均等于 `--limit-rate`
351: - **取消是协作式的**：正在阻塞的网络读要等本次写回调或超时才退出
352: - **续传沿用旧的分片计划**：只有新建任务才会按当前线程数重新规划分片
353: - **`ETag` / `Last-Modified` 都缺失时无法续传**：会从头下载
354: - **不支持 Cookie 文件**：只能用 `-H "Cookie: ..."` 手动传
